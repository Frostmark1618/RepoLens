# RepoLens Q&A Forensic Audit — 2026-09-30

## Scope
This audit uses the uploaded RepoLens ZIP as the authoritative release source and focuses on the Repository Q&A path.

## Root cause found
`RepositoryService.ask()` loaded `repository_analysis.json` but did not pass the loaded analysis into `answer_repository_query()`. The Q&A pipeline therefore had repository code chunks and architecture facts, but no first-class evidence path for repository-wide metadata such as total files and Python-file count.

This caused metadata questions to fall through to retrieval/LLM behavior:
- Python files could be hallucinated.
- Total files could become UNKNOWN.
- Similar repository-wide metadata questions were vulnerable to the same failure.

## Correction
Added a repository-metadata evidence contract:
- `retrieval/metadata_evidence.py`
- `RepositoryService.ask()` now passes authoritative repository analysis into Q&A.
- Metadata evidence is retrieved independently from code-chunk retrieval.
- Metadata facts are available to focused RAG context.
- Metadata facts are independently claim-verified.
- Metadata verification has precedence over architecture verification so dependency-graph edge count and architecture edge count cannot be confused.
- Metadata questions can be answered deterministically without Ollama.
- Public evidence and retrieval counts expose metadata evidence.

## Security correction
Added `llm/qa_safety.py` to block direct secret-value disclosure requests before retrieval/LLM generation (API keys, passwords, access tokens, private keys, credentials, environment values). This does not block ordinary questions about security controls or whether secrets are hardcoded.

Repository evidence remains explicitly untrusted data in both answer-generation and claim-verification prompts.
